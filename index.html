      What's new in 3.0
      
The biggest release yet.
The smallest dependency tree ever.

      
Axiom 3.0 replaces the JDBC and Vert.x engines with five native drivers, moves parsing off-heap onto
        MemorySegment, and splits the forensic flight recorder out into its own module.

    


    

      

        

        
Native drivers through Project Panama

        
Every driver binds the vendor's own C client with the Foreign Function & Memory API. Connections are created per
          wield(..) inside a confined Arena, and they're closed and freed before the call returns.
          Nothing is pooled, and nothing leaks between calls.

        

          your code→JDBC→pool→Panama downcall→libpq · OCI · ODBC→database
        

        
postgresqlmysqloraclesqlitesqlserver

      


      

        

        
axiom-telemetry

        
A rolling black-box recorder. When an operation fails, the failure arrives with a snapshot of everything that succeeded just before it.

        
new modulelock-free

      


      

        

        
Off-heap parsing

        
JsonParser, CsvRowParser, AxiomDopParser and SchemaGuard all read a MemorySegment directly. They can read files memory-mapped from disk, without first copying them into a byte[].

      


      

        

        
Contract-verified bulk ingest

        
Before a single CSV row is sent, Hammer checks your declared headers and types against the live catalog and reports every mismatch at once.

      


      

        

        
Scoped native memory

        
BoundScope binds a confined arena to each call through ScopedValue. It has no thread-locals and no finalizers, and it runs safely on virtual threads.

      


      

        

        
Typed binds, native syntax

        
You write :java.name once. Each driver rewrites it to the engine's own placeholder ($1, :1 or ?) and binds it out-of-band with an explicit type.


dynamicQuery("… WHERE status = :java.status LIMIT :java.limit")
  .to("ACTIVE").bind(PostgresType.TEXT)
  .to(10).bind(PostgresType.INT8)

      


      

        

        
Ten modules, one version

        
The stack has five core modules and five drivers, all at 3.0.0 and all signed and published together. Each is a plain JAR with its own JPMS automatic module name, and you import only what you use.

        
axiom←sovereign←language·spec←warp-*-driver·telemetry

      Anatomy of a request
      
From socket to SQL and back, in six honest steps.

      
This is a real handler from the 3.0 reference strike. Scroll through it: every step is a function call you can read, and there's no framework hiding the rest.

    

    

      

        
01
Bytes arrive
The request body becomes a MemorySegment. Parsers read it in place, without building intermediate Strings.
java.lang.foreign

        
02
Parse and guard the perimeter
JsonParser builds a frozen PersistentMap, and SchemaGuard validates it against a cached .axiom schema. The first violation comes back as a Result, with its exact path.
axiom-spec · axiom-language

        
03
Extract typed values at the edge
The data stays untyped inside. Types are asserted only where you need them, with targetKey(..).toStringVal().
axiom

        
04
Wield a native connection
wield binds a confined arena, opens one libpq connection, runs your lambda and always disconnects, whether it succeeds or fails.
axiom-warp-postgresql-driver

        
05
Bind out-of-band with explicit types
Each :java.name becomes $n and goes through PQexecParams with an explicit OID. Values never touch the SQL text.
PostgresType

        
06
Emit immutable rows
Rows come back as a PersistentList<PersistentMap>. map shapes the response, and JsonEmitter writes it out. Failures stay values the whole way.
axiom · axiom-spec

      Quickstart
      
    Query PostgreSQL natively in four steps.
    
    
    
    
    
      
    Add the driver
    It brings in axiom-spec and axiom transitively.
    

    <dependency>
  <groupId>com.ensemblu</groupId>
  <artifactId>axiom-warp-postgresql-driver</artifactId>
  <version>3.0.0</version>
</dependency>
    
      
    Describe the perimeter
    Put a plain properties file on the classpath. There's no JDBC URL and no pool to tune.
    

    engine.host=localhost
engine.port=5432
engine.dbname=axiom_demo
engine.user=axiom_commander
engine.password=strike_hard
    
      
    Provision the executioner
    The curried chain makes a missing step a compile error, and a bad value fails at boot.
    

    var pg = PostgreSQL
  .connect(file("database.properties"))
  .requiredHost().requiredPort()
  .requiredDbName().requiredUser()
  .optionalPassword()
  .getPostgreSqlDriverOrThrow();
    
      
    Wield a query
    You get a Result of immutable rows. Nothing throws unless you ask it to.
    

    var rows = pg.wield(conn ->
  pg.dynamicQuery(
    "SELECT * FROM accounts WHERE status = :java.s")
  .to("ACTIVE").bind(PostgresType.TEXT)
  .execute(conn));
    
    
    
    
    
      
      
    Runtime flags. Axiom 3 compiles against Java 26 preview APIs, so run with --enable-preview. Add --enable-native-access=ALL-UNNAMED to silence restricted-method warnings for the Panama downcalls.
        The vendor client (libpq, libmysqlclient, Oracle Instant Client, sqlite3 or an ODBC driver) has to be findable by your OS loader. On Windows, that means it's on PATH.

      FAQ
      
    Questions engineers actually ask.
    
    
    
    
    
      
    Why drop JDBC entirely?
    JDBC is an abstraction over vendor wire protocols, and it brings type inference, driver-specific quirks and, in practice, a pool and its tuning along with it. Since Project Panama is final, Java can call the vendor's own C client directly. So that's what Axiom 3 does: one explicit downcall per operation, with typed parameters and nothing in between.
    
      
    No connection pool? Isn't that slow?
    Each wield(..) opens a dedicated native connection and closes it when the call returns. That makes resource ownership trivial, with no leaked connections and no shared state, and it fits virtual threads. Put batches, transactions and related reads inside a single wield so they share one session. For very high request rates, measure against your own latency budget; it's an explicit trade-off, and it's documented as one.
    
      
    Which Java version do I need?
    Java 26. Axiom uses java.lang.foreign, ScopedValue and other modern APIs, and it's compiled with --enable-preview, so your application must run with --enable-preview too.
    
      
    Do I need the native client libraries installed?
    Yes. That's the point: Axiom ships no wire-protocol reimplementation. Install libpq (PostgreSQL), libmysqlclient (MySQL), Oracle Instant Client, sqlite3, or the Microsoft ODBC Driver 18 for SQL Server, and make sure the OS loader can find it.
    
      
    Can I still use Axiom without a database?
    Absolutely. axiom on its own gives you persistent collections, Result, guards, navigation, config and effects. Add axiom-spec for JSON/CSV, axiom-language for schema validation, and axiom-telemetry for failure forensics. None of these touch a database.
    
      
    What happened to axiom-warp-jdbc and axiom-warp-reactive?
    They're retired in 3.0. The native drivers replace the JDBC engine, plain virtual threads replace the Vert.x engine's concurrency, and the reactive engine's forensic history now lives in axiom-telemetry. The 2.x artifacts stay on Maven Central. See the migration guide above.
    
      
    Is it safe against SQL injection?
    PostgreSQL, Oracle, SQLite and SQL Server send values out-of-band as typed parameters, so values never become SQL text. The MySQL C API has no out-of-band text-protocol parameters, so its driver escapes each value through mysql_real_escape_string before quoting it with bindQuotedValue. Use bindValue only for trusted numeric literals.
